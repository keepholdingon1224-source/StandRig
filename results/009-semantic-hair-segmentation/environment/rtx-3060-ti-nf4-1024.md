# 実験009-A ローカル RTX 3060 Ti 8 GB 実行手順

Kaggleの無料APIバッチではL4を利用できなかったため、ローカルの公式NF4・1024を次に試す。実機操作はMUSE・ユーザーと連携し、追加課金なしで実施する。手順の状態は準備済み、実機未検証。[構成別判定](environment-report.json)

## 環境と重み

以下は Bash の例。StandRigの指定実験ブランチとSee-throughを別々の作業先に置く。Windowsでは既存のCUDA対応環境に合わせてvenvの有効化とパス指定を置き換える。実験データ、キャッシュ、重みは指定作業先に置く。以下の記録ディレクトリは新規作成する。

```bash
git clone https://github.com/shitagaki-lab/see-through.git
git -C see-through checkout --detach fc4440db7c076518e313f378e28b1504e9886a95
python3.12 -m venv .venv-009
source .venv-009/bin/activate
python -m pip install torch==2.8.0+cu128 torchvision==0.23.0+cu128 torchaudio==2.8.0+cu128 \
  --index-url https://download.pytorch.org/whl/cu128
python -m pip install -r see-through/requirements.txt -r see-through/requirements-inference-bnb.txt psutil==7.2.2
mkdir run-nf4-preflight
nvidia-smi > run-nf4-preflight/nvidia-smi.txt
python -m pip freeze > run-nf4-preflight/pip-freeze.txt
```

[モデル固定記録](model-revisions.json)のNF4欄を使う。Marigoldの短縮SHA `e53b344` は、モデルレジストリに接続できる実行先で `HfApi().model_info(repo_id, revision="e53b344").sha` により解決し、40桁SHAと固定リビジョンのREADME・LICENSE・NOTICEを記録する。両モデルの `snapshot_download(repo_id, revision=完全SHA)` で得た実ファイルをSHA-256で計測し、相対パスとバイト数を保存する。公開LFSのSHA-256が取得できるファイルは照合する。診断と本実行で同じスナップショットを使う。

ランナー入力用の `revisions-nf4.json` は、上記で確認したNF4のモデルID 2件をキー、各40桁SHAを値とするJSONオブジェクト。ランナーは固定コードと追跡ファイルの状態を検査し、固定スナップショットを取得・ハッシュ化してから、公式推論をオフラインで起動する。

## Attention事前診断

1. **モデル読み込み前。** Python、PyTorch、CUDAビルド、NVIDIAドライバ、bitsandbytesの版と、GPU名・Compute Capability・総/空きVRAMを記録。CUDAの可否と `torch.cuda.is_bf16_supported(including_emulation=False)` を確認する。小さなCUDA BF16テンソルでSDPAを実行し、PyTorchの各SDPAバックエンドの有効フラグとProfilerの演算イベントを保存する。
2. **実入力の短い診断。** 固定済み重み・1024・グループオフロードで初回LayerDiff Body処理に進む。最初のSDPAから形状が変わる主要な呼び出しまで、外部診断ラッパーでQ/K/V形状・dtype・stride・device、マスクの形状とdtype、causal・dropout・GQAを呼び出し前にログへ出す。小テンソルの結果と実入力の結果は別に残す。
3. **適合性と実選択の確認。** 同じ引数から `torch.backends.cuda.SDPAParams` を作り、Flash・Efficient・cuDNNの `can_use_*_attention(..., debug=True)` の判定と警告、Mathの有効フラグを記録する。Mathの中間メモリは形状から見積もり、実形状で省メモリ候補がすべて不適合なら本実行を止め、理由を残す。適合する入力では強制指定を入れず、Profilerのカーネル別演算イベントで実際の選択を確認する。一般のSDPA演算名だけが得られた場合、実際のバックエンドは未確認と記録する。診断プロセスの途中終了は意図した終了として記録する。
4. **本実行の計測。** VAE・Body・Head・Marigoldの段階を識別して、可能な範囲で同じ推論プロセス内の `max_memory_allocated()` と `max_memory_reserved()` を段階終了時とOOM時に記録する。既存ランナーのデバイス使用量・プロセスツリーRSSのサンプルに加え、システムの使用/利用可能RAMを時系列で残す。計測は外部ラッパーで行う。公式コードへの変更が必要な場合は別試行として差分を保存し、公式方式の結果と区別する。

## 本実行と評価

診断通過後、同じvenvから素材1で最小試験を行う。以下はStandRigとSee-throughが同じ親ディレクトリにある場合の例。

```bash
python StandRig/experiments/009-run-seethrough.py \
  see-through StandRig/source_007/original.png run-nf4-1024 revisions-nf4.json \
  --mode nf4 --resolution 1024
```

公式NF4 CLI相当の構成は1024・深度768・seed 42・30ステップ・グループオフロード・PSD出力。成功時は `layer_smoke_pass`、PSD、意味レイヤーの可読性、入力との位置合わせを確認する。失敗時も `run.json`、`inference.txt`、GPU/RAMサンプルと診断ログを回収し、`SHA256SUMS` を照合する。

ランナーはPSDのレイヤーオフセットで配置し、アルファを元画像の長辺まで補間して中央パディングを除去する。その後、アルファ128以上の前面所有から可視マスクを抽出する。既に二値化したマスクを座標変換する場合は最近傍補間を使う。正式評価は素材1の幅1152×高さ2048を含む各原画像の座標系。左右の可動毛束・スカートを009の共通ルールで割り当て、素材別手指定ゼロ、2素材の全6項目でIoU 0.90以上を求める。最小試験の成功は正式IoU判定と別に記録する。

ローカルGPU構成が成立しない場合、Kaggle T4でのNF4・1024はAttention OOMの再発可能性を踏まえて検討する。GPU環境が成立しない場合の代替順はAnimeSeg＋MobileSAM、Grounding DINO＋SAM。005〜008・固定基準マスクを保護し、SONY共同プロジェクトと完全に分離する。
